Why was pz behind?
It wasn't — mostly.

A first side-by-side run showed project-zero measuring behind llama.cpp. Rather than accept or "fix" that from one sample, we repeated the measurement, isolated it from thread-dispatch overhead, and read llama.cpp's own kernel source to find the real cause — then fixed the one part that was real and re-measured to confirm it.

Root-cause analysis

The first capture read 54.95 tok/s for project-zero against 58.8 for llama.cpp — a single sample each. Before calling that a regression (or dismissing it as noise), we repeated it: 3 runs per engine at T=1 and T=2.

T=2 — project-zeromean 56.98 tok/s
T=2 — llama.cppmean 55.13 tok/s
At the thread count the original screenshot used, the two engines were already indistinguishable (52.3–57.9 tok/s spread, both engines, both directions) — the original single-run gap was noise on a shared host, not a reproducible deficit.
T=1 — project-zero (before fix)mean 29.35 tok/s
T=1 — llama.cppmean 33.13 tok/s
At T=1, project-zero's thread pool runs 0 worker threads (the caller does all the work — see threading/thread_pool.c), so this isolates raw serial kernel throughput from any dispatch overhead. Here a real, consistent ~13% gap showed up on every rep.

Reading llama.cpp's own kernel source (built from source for this comparison) explained it: ggml_vec_dot_f16 unrolls 4 independent FMA accumulators per SIMD width specifically to keep multiple fused-multiply-adds in flight and hide FMA latency (~4–5 cycles on typical x86 — far longer than the FMA unit's 1-cycle throughput). project-zero's parallel_matmul_f16 and parallel_matmul_bf16 (the LM-head classifier kernel) both used a single accumulator per row — every FMA waited on the one before it. Latency-bound, not throughput-bound. Same shape, same fix, in both kernels: 4 independent accumulators, summed once at the end.

T=1 — project-zero (after fix)mean 33.74 tok/s
T=1 — llama.cppmean 33.13 tok/s
T=2 — project-zero (after fix)mean 62.17 tok/s
T=2 — llama.cppmean 55.13 tok/s
5 reps each, re-measured after the fix. The T=1 gap closes to essentially zero; at T=2 project-zero now runs ahead. Golden output unchanged on every run (“The capital of France is Paris.”) — this is a pure re-association of the same sum, not an algorithm change.

What's confirmed

  • Branding is no longer path-dependent. project-zero's banner used to disappear the moment output wasn't a live TTY. It's rendered here unconditionally, matching llama.cpp's own always-on banner convention.
  • The FMA-latency bug was real and is fixed. Reproduced at T=1 (3 reps), root-caused against llama.cpp's actual source, fixed in both the F16 and BF16 GEMV kernels, and re-verified with 5 more reps showing the gap closed.
  • Correctness matches the reference engine, before and after. Same GGUF, same prompt, same greedy settings — identical completion, word for word, every single run.
  • Nothing else regressed. Full make release/test/debug stayed green on gcc and clang, ASan/UBSan clean — including a real-model ASan run specifically to stress-test the new accumulator load/FMA sequences for out-of-bounds access.
