project-zero exposes three independent runtime levers (--threads, --simd, --classifier) — a full cross-product sweep, 48 configurations. llama.cpp exposes exactly one of those as a runtime flag on this build (--threads); its SIMD backend and weight precision are fixed at build/conversion time, not chosen per run. So the honest comparison is: the full 3-axis sweep for project-zero, a 1-axis sweep for llama.cpp, and a same-axis (thread-count) comparison where both actually vary the same thing.

Method & two real detours

Model: SmolLM2‑135M‑Instruct (F16 GGUF), greedy decoding (temp 0), one shared 4-core host, single rep per configuration — this is a directional sweep across 52 configurations, not the repeated-measurement statistical comparison done earlier for the T=1/T=2 RCA (see docs/ai/decision-log.md's 2026-07-24 entries); treat single cells as approximate, not to the decimal.

Revision note: the first pass of this sweep used the prompt “What is the capital of France?” with --max-tokens 30. The model answered in 7 tokens and hit its EOS token immediately — every tok/s figure in that pass was computed over a 7-token, sub-200ms window, dominated by process/timer noise rather than steady-state throughput. Caught by a reviewer asking "shouldn't this capture at least 240 tokens given the speeds involved?" — correct, and it didn't. Reran the entire sweep (all 52 configurations) with a long-form creative-writing prompt (“Write a long, detailed story about a robot exploring an ancient forest...”) that reliably avoids early EOS, and --max-tokens 250; every run in this report generated 251 real tokens. All numbers below are from the corrected pass.

Mid-sweep, project-zero started crashing (SIGILL) on every invocation, including completely flag-free ones. Caught it live under gdb: a vpermi2b (AVX-512 VBMI) instruction inside the calibration routine — this CPU's flags don't include VBMI. Not a code bug: -march=native (what make release/make debug use) bakes in whatever the build machine's cpuid probe reports, which apparently doesn't match what this sandboxed host can actually execute. Rebuilding with make dist (the project's own portable target, -march=x86-64-v2 baseline with the real SIMD kernels still per-file-compiled and runtime-dispatched) fixed it outright — logged in mistakes.md so it doesn't need re-diagnosing.

Second detour, found while recapturing screenshots for this revision: taking a terminal screenshot of one engine while the other engine's sweep was still running in the background silently corrupted the measurement — llama.cpp's T=4 run (all 4 threads) measured 7.4 tok/s against a clean 62.9 tok/s rerun, because a concurrent project-zero screenshot capture was contending for the same 4 cores. Fixed by never running two CPU-bound captures at once on this host, and re-verified every screenshot's reported tok/s lands within normal single-run variance of its corresponding sweep-CSV cell before trusting it.

One consistent pattern across all three panels, confirmed now with real 251-token generations (it also held in the earlier 7-token pass, but that pass couldn't rule out measurement noise as the cause): INT4 classifier is slower than BF16 or INT8 on this model, at all 16 thread×SIMD combinations — the opposite of what the classifier-quantization comment in src/cli/main.c estimates for larger models. The INT4 captures also show a qualitative symptom: output degenerates into repetitive looping text well before 251 tokens (see the INT4 screenshot above), which BF16/INT8 do not. Not chased further here (out of scope for this sweep); worth its own RCA, and the repetition may be the more actionable finding of the two.

What this sweep shows

  • Both engines scale with threads as expected — roughly linear T=1→T=3, flattening toward T=4 on this 4-core host (thread-pool/scheduling overhead catching up with available parallelism).
  • No single SIMD backend dominates for project-zero on this tiny 135M model — scalar, avx2, avx512f and vnni all land within noise of each other at a given thread/classifier, consistent with this model being far under project-zero's measured bandwidth ceiling (compute/dispatch-bound, not bandwidth-bound) at this size.
  • Matched on threads (the only axis both expose), the two engines are effectively tied — project-zero fractionally ahead at T=1 (26.0 vs 24.8) and T=2 (42.7 vs 41.0); llama.cpp fractionally ahead at T=3 (55.6 vs 55.3) and T=4 (62.9 vs 62.1). All four pairs are within ~3% of each other. Consistent with the earlier RCA finding that this comparison is now roughly even, not a deficit — and this time backed by full 251-token runs instead of a 7-token snippet.
  • All 251-token generations completed as coherent English for BF16/INT8 across all 52 runs; INT4 runs are fluent early on but reliably degenerate into looping repetition before the token budget is used up (see the INT4 screenshot) — a quality regression that tracks the same classifier, not a one-off.
